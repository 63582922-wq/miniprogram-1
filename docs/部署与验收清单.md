## 二、部署失败的根因（已解决，记录备查）

首次部署连续失败，报错：

```
getCloudAPISignedHeader failed: {"base_resp":{"ret":41002,"errmsg":"system error."}}
```

**根因有两个，叠加在一起：**

### 1. 系统全局代理拦截了腾讯域名

本机 `捷豹加速3.0`（FlClash 内核）设置了系统级代理 `127.0.0.1:7990`，
例外列表只包含知乎、京东、讯飞和内网段，**没有任何腾讯域名**。实测：

| 域名 | 直连 | 经代理 |
|---|---|---|
| `pay.qq.com` | **200** | **000 连接失败** |

`000` 对应浏览器里的 `ERR_CONNECTION_CLOSED` —— 这才是**支付页一直打不开**的真正原因，
跟账单无关。退出加速器后系统代理设置**没有被自动还原**，仍指向已无人监听的
`127.0.0.1:7990`，反而更糟。已用 `networksetup -set*proxystate off` 关闭全部代理。

> 教训：做云开发相关操作（部署、支付、控制台）前，先退出代理类软件。

### 2. `--project` 参数不会把 AppID 带上

`41002` 的含义是 **appid missing**。CLI 帮助写着 `--appid` 在给了 `--project` 时被忽略，
而实际行为是**给了 `--project` 反而完全不带 AppID**。改用 `--paths` + `--appid` 即可（见第四节）。

### 3. 首次部署需要跑两遍

第一遍创建函数，紧接着的代码上传会因为函数仍处于 `Creating` 状态而失败
（`FailedOperation.UpdateFunctionCode`）。这不是错误配置，等 1–2 分钟重跑一次即可。
期间函数的「创建」其实已经成功，工具报的失败是**误报**——因为响应被死代理吞掉了。

### ⚠️ 旧环境已无法恢复

`cloud env list` 确认现在只剩 `cloud1-d4ge4gu1le8fe61d3` 一个环境，
旧环境 `cloud1-2gx2o7qj5893195c` 已不存在。

微信云开发环境**过期后会连同其中所有云函数、数据库记录、云存储文件一起删除**。
旧环境过期至今约四个月，通常已超出数据保留宽限期，**原有项目、巡查记录与照片大概率无法找回**。

这就是「自动续费」必须打开的原因 —— 控制台里它目前仍是关闭的，
不打开的话 **2026-10-15 会再次失效**，同样的事会重演一遍。

**建议现在就去控制台确认两件事：**
1. 打开 **自动续费**（必须）
2. 评估是否打开 **按量付费**（关闭状态下配额用尽服务会直接不可用；商用建议打开）

## 三、数据库集合（10 个）

**新环境里一个集合都没有**，必须先建。微信云开发**不会在写入时自动建集合**，缺集合会直接报 `-502005 database collection not exists`。

### 推荐做法：用 `setupdb` 函数一次建齐

已新增 `cloudfunctions/setupdb/`，它会幂等地创建下面 10 个集合（已存在的跳过，可重复调用）。

1. 先按第四节把 `setupdb` 部署上去
2. 开发者工具 → **云开发控制台 → 云函数 → setupdb → 云端测试 → 直接调用**
3. 返回结果里看 `created` / `skipped` / `failed` 三个数组
4. 建完后这个函数就可以删掉了

### 手工做法：控制台逐个新建

在「云开发控制台 → 数据库 → 新建集合」中依次创建：

```
users              用户
projects           项目
inspections        巡查
inspection_items   巡查问题项
reports            报告
memos              待办备忘
chat_analysis      聊天整理
app_settings       公司与巡查人设置
subscriptions      订阅消息授权
ai_tasks           AI 异步分析任务
```

### 建议创建的索引

新建集合后默认无索引，列表查询会随数据增长变慢，且云开发单次查询默认只返回 100 行，**超出部分会被静默截断**（看板计数会偏小）。建议按下表建索引：

| 集合 | 索引字段 | 说明 |
|---|---|---|
| `users` | `openId` | 唯一索引 |
| `app_settings` | `openId` | 唯一索引 |
| `projects` | `ownerOpenId` + `deleted` + `updatedAt` | 项目列表 |
| `inspections` | `projectId` + `deleted` + `createdAt` | 项目内巡查列表 |
| `inspections` | `inspectorOpenId` + `deleted` + `createdAt` | 我的巡查 |
| `inspection_items` | `inspectionId` + `deleted` + `sortOrder` | 巡查详情 |
| `inspection_items` | `projectId` + `deleted` | 项目问题统计 |
| `reports` | `projectId` + `deleted` + `generatedAt` | 报告列表 |
| `reports` | `inspectionId` + `deleted` | 按巡查查报告 |
| `memos` | `createdBy` + `deleted` + `createdAt` | 待办列表 |
| `subscriptions` | `openId` + `scene` | 授权查询 |
| `ai_tasks` | `status` + `createdAt` | 任务调度 |

> 数据库权限建议全部选 **「仅管理端可读写」**。所有读写都经云函数，前端不直连数据库。

## 四、部署云函数（10 个）

集合建好后，用下面任一方式部署。**必须选「云端安装依赖」**——本地没有 `node_modules`，而 `ai`、`chat`、`speech` 依赖 `axios` 与 `tencentcloud-sdk-nodejs`。

### 方式 A：命令行（推荐，一条命令）

**必须用 `--paths` + `--appid`，不要用 `--project`。**

实测：`--project` 会报 `getCloudAPISignedHeader failed: ret:41002`，而
`41002` 的含义是 **appid missing**（[微信开放社区](https://fuwu.weixin.qq.com/community/develop/doc/00048e9a8700984ebd5dc222c56000)）。
也就是说给了 `--project` 之后 CLI 反而没把 AppID 带上。用 `--paths` 显式指定函数目录、
用 `--appid` 显式给 AppID 才能成功。

```bash
cd /Users/cft/WeChatProjects/miniprogram-1
P=/Users/cft/WeChatProjects/miniprogram-1/cloudfunctions
CLI=/Applications/wechatwebdevtools.app/Contents/MacOS/cli

$CLI cloud functions deploy \
  --env cloud1-d4ge4gu1le8fe61d3 \
  --appid wxf30ba9025bea84ab \
  --paths $P/auth $P/project $P/inspection $P/memo $P/report \
          $P/settings $P/subscribe $P/ai $P/chat $P/speech $P/setupdb \
  --remote-npm-install
```

> **首次部署要跑两遍。** 第一次会把函数创建出来，但紧接着的代码上传会因为函数仍处于
> `Creating` 状态而失败（报 `FailedOperation.UpdateFunctionCode`）。等 1–2 分钟再跑第二遍，
> 这一次走「更新」路径就能成功。这是微信侧创建与上传的时序问题，不是配置问题。

### 方式 B：开发者工具界面

在左侧 `cloudfunctions` 下，对每个函数右键 → **上传并部署：云端安装依赖**。

**方案 2 · OpenAI 兼容接口（支持多模态，推荐用 DeepSeek）**

**推荐配置：DeepSeek V4.1-Flash**

| 变量 | 值 |
|---|---|
| `AI_API_KEY` | DeepSeek API Key（platform.deepseek.com） |
| `AI_BASE_URL` | `https://api.deepseek.com` |
| `AI_MODEL` | **`deepseek-flash`** |

> ⚠️ **模型名是 `deepseek-flash`，不是 `deepseek-v4.1`。**
> 官方在 2026-09-10 的 GA 版把 `deepseek-v4-flash` 与
> `deepseek-v4-flash-vision-exp` 归并到 `deepseek-flash` 这**一个 id**。
> 填旧名也能路由过去，但直接用新名最稳。

**为什么适合这个场景**（官方公布的视觉基准）：

| 基准 | 分数 | 对应的产品需求 |
|---|---|---|
| DocVQA | 95.6 | 从照片读取细节——裂缝、留缝、标签 |
| RefCOCO | 86.0 | 定位指定物体——对应「标注」 |
| CVBench | 77.9 | 计数与空间关系——墙砖错缝、间距不均 |
| MMMU-Pro | 56.5 | 图文综合推理 |

**价格**：输入 `$0.15`/1M（缓存未命中、非高峰）、输出 `$0.60`/1M。
单张图按约 384 input tokens 封顶计算，**一张图约 `$0.0001`**，
一千张图一毛多美金——对这个成本结构可以忽略。

**其他可选变量**

| 变量 | 说明 |
|---|---|
| `AI_IMAGE_DETAIL` | 图片精细度，默认 `high`。巡检照片要看清毫米级差别（裂缝宽度、留缝是否一致），所以默认要求原分辨率。设成**空字符串**则不发送该字段，用于兼容不支持 `detail` 的服务商 |
| `AI_PROVIDER` | 仅当用智谱时需要填 `zhipu`（会带上 thinking 参数）。用 DeepSeek 时**留空** |
| `AI_THINKING` | 可选，`enabled` / `disabled`，仅对智谱生效 |

> 代码已经实测与本格式兼容：system 用纯文本、user 用 `content` 数组承载
> `{"type":"text"}` 与 `{"type":"image_url"}`，与 DeepSeek 的 OpenAI 兼容接口一致。
> 注意图片只能放在 **user** 消息里，放 system/assistant 会返回 400——现有代码本来就是这么组织的。

## 九、PDF 服务器待修（独立问题）

`pdf.haolizhiguan.cn` → `49.232.215.168`（腾讯云），现状：

| 检查 | 结果 |
|---|---|
| DNS 解析 | ✅ `49.232.215.168` |
| 80 端口 HTTP | ✅ 302（nginx 活着，正常跳转 HTTPS） |
| 443 端口 TCP | ✅ 可连接 |
| 443 端口 HTTPS 握手 | ❌ **被立即重置**（`Recv failure: Connection reset by peer`） |

80 通、443 被重置，通常意味着 **443 上有进程在监听但 TLS 没配好**
（例如 nginx 的 443 server 块证书路径失效，或 443 被别的进程占用）。

### 服务器登录方式

```bash
ssh ubuntu@49.232.215.168
```

- 用户：`ubuntu`（本机 `~/.ssh/id_ed25519` 未被授权，需用密码）
- 密码忘记时走腾讯云网页控制台 → 轻量应用服务器 / 云服务器 → 找到该 IP → 远程连接

### 服务运行方式

- 目录：`/home/ubuntu/report-pdf-service`
- 进程管理：**pm2**，服务名 `report-pdf-service`
- 历史部署方式：本地 `tar` 打包（含 `node_modules`）→ `scp` 上传 → `pm2 restart`

### 诊断命令

```bash
pm2 list
pm2 logs report-pdf-service --lines 40 --nostream
systemctl status nginx --no-pager
nginx -t
sudo ss -lntp | grep -E ':80|:443|:3100'
sudo tail -30 /var/log/nginx/error.log
sudo ls -la /etc/letsencrypt/live/ 2>/dev/null || sudo ls -la /etc/nginx/ssl/ 2>/dev/null
```

### 修好后必须做的事

服务器上跑的还是**旧代码**，仓库里的安全加固（fail-closed、XSS 转义、
SSRF 白名单、临时文件回收）需要重新部署才生效。

**旧代码的问题**：`PDF_API_KEY` 不配置也放行，等于接口对公网开放，
任何人都能驱动 Puppeteer 消耗服务器资源。

重新部署时务必带上密钥：

```bash
cd /home/ubuntu/report-pdf-service
sudo PUPPETEER_SKIP_DOWNLOAD=true npm install
PDF_API_KEY=<设一个强随机串> pm2 restart report-pdf-service --update-env
pm2 logs report-pdf-service --lines 20
```

同时 `report` 云函数的环境变量里要填同名的 `PDF_API_KEY` 与 `PDF_SERVICE_URLS`。

### 建议用 systemd 托管（避免进程挂掉没人拉起）

```ini
# /etc/systemd/system/report-pdf.service
[Unit]
Description=Report PDF Service
After=network.target

[Service]
```
