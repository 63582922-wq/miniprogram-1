## 2. 部署前检查

只有在用户/环境负责人明确授权具体环境与动作后，才进入云端部署。部署前逐项留存：

1. 确认 AppID、云环境 ID、该环境用途、目标函数、授权执行人，以及是否允许在隔离测试账号/项目写入。若无法确认环境是否生产，停止部署。
2. 记录每个受影响云函数的当前版本/配置、运行时、超时、内存、依赖和环境变量名称；备份可恢复的函数版本与安全规则。不要把密钥写入代码、Git、截图、终端回显或日志。
3. 确认变更清单和依赖：先读目标目录的 `package.json`，确保新增模块（例如 `cloudfunctions/ai/text-organizer.js`）随 `index.js` 一起进入部署包，并在云端安装正确依赖。不能只上传单个入口文件。
4. 核实集合、索引、安全规则与云函数调用方兼容性。至少确认项目/巡查/报告归属校验、稳定请求 ID、旧字段兼容、任务读取与推进分离，以及报告快照仍按原合同读写。不要运行会覆盖集合/规则的 `setupdb` 初始化。
5. AI/ASR 真实调用前，先由账号持有人核实供应商、模型、单次费用、额度、重试规则和隔离测试范围；得到针对该次调用的明确许可后，才做最少量验证，并记录请求数、结果和实际账单。未通过此闸口只运行模拟夹具，不做在线模型探测。
6. 真机验收需要用户提供可用的 iOS/Android 环境；跨账号分享需第二微信。开发者工具模拟器、源代码检查和自动化不能替代这些验收。

## 3. 建议部署顺序（不是当前授权）

以下是取得明确授权后的操作顺序，不代表本轮已执行：

1. 保存当前客户端/云函数版本、配置与隔离数据快照；确认恢复路径可用。变更前后都不得改真实客户记录。
2. 先部署兼容云函数，后切客户端。仅部署本次变更所需函数；如 AI 变更涉及新字段/任务行为，先确保旧客户端仍可读旧结构，新客户端也能兼容旧数据。
3. 只读核实云端函数状态、运行时、配置与部署版本；确认返回真实是目标版本，不以“上传成功” toast 作为完成证明。
4. 在隔离 QA 项目做最小手动路径：照片归属正确、说明/标注可恢复、人工核对后生成在线报告、从报告列表重开同一快照。AI/ASR 只在第 2 节计费闸口通过后单独验证。
5. 检查在线报告含照片、编号、确认文字与所需企业/巡查资料；只读分享验证必须在作者与接收者两侧完成。未有第二微信则记“未验证”。不生成 PDF。
6. 完成受影响项回归后，再由用户决定是否上传体验版；公众发布/提交审核是另一个审批关口，不在自动流程中。

出现跨项目错配、数据丢失、重复报告、标注与问题错配、越权读取、旧报告内容变化或报告无法重开，立即停止扩大验证，不继续写入隔离数据，先按实际影响评估修复与回退。

## 4. 回退策略

- **客户端：**恢复已记录的上一可用版本；保留新云函数字段和本地/云端草稿，不批量清理。旧客户端可能不理解新版未完成草稿，恢复后先验证只读打开与草稿保留，不让旧版本覆盖新结构。
- **云函数：**以函数为单位回退到部署前已记录且与现有数据合同兼容的版本。新旧端并存期间保留新增字段；不得直接切换到会忽略报告快照或任务状态的旧逻辑。若兼容性未知，先禁用受影响的新入口并保护数据，不能臆测无损回退。
- **报告/分享：**在线报告依据发布时冻结的快照。修复不能回写已发布快照；分享撤销只按明确操作处理在线链接。任何已经被接收者查看或另行保存的内容都不能靠服务端回退抹除。
- **禁止事项：**不清空集合、不批量回迁、不撤销所有客户链接、不覆盖媒体文件；先精确列出受影响的隔离记录并留备份，再按单条、可恢复方式处理。

## 5. 本地复核与证据

在项目根目录运行：

```sh
node --test tests/*.test.cjs
node tests/local-compile.cjs
git diff --check
```

这些检查验证本地逻辑/模板，不证明云端部署、真实模型效果、设备行为或分享接收成功。最终体验版交付前的证据应包括：

- 唯一执行计划与实际测试走查记录；本地回归结果及其覆盖范围。
- 隔离项目中真实测试照片的采集、标注、人工核对、在线报告发布与重开记录；照片/问题/编号对应关系。
- 目标环境、云函数部署前后版本及回退版本；账号持有人核准的真实调用台账（若批准 AI/ASR 调用）。
- iOS/Android 真机系统与基础库、关键手势/权限/安全区实测；第二微信只读分享结果。不能实测的项目明确保留为“未验证”。
- 体验版版本号与回退入口。公众发布不属于体验版验收自动步骤。
