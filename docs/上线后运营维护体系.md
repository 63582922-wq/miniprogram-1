# 上线后运营维护体系

> 生成于 2026-10-08。所有数字来自逐行读码与实测，标注「估算」的部分给出推算依据。
> 本文回答一个问题：**用户变多之后，会发生什么、提前做什么、出事了怎么办。**

---

## 一、先说结论：三个会最先出问题的地方

按「多快会发生」排序：

| # | 问题 | 触发条件 | 后果 |
|---|---|---|---|
| 1 | **数据库没有索引** | 单集合超过几千行 | 查询变慢 + **费用随行数线性上涨**（云开发按读取次数计费，无索引=全表扫描） |
| 2 | **照片是原图，无压缩** | 几十个活跃项目 | 存储与流量成本快速上涨；报告每被查看一次就重新下载全部原图 |
| 3 | **AI / ASR 按量计费** | 用户开始用 AI 识图 | 费用与调用量同比例增长，且**没有限额保护** |

前两个是工程问题，**现在就能修**；第三个是成本控制，需要配额与告警。

## 二、当前系统的规模特征（事实）

### 数据库集合与查询模式

`setupdb` 只创建集合，**没有创建任何索引**（`createIndex` 在全仓出现 0 次）。实际查询如下：

| 集合 | 查询条件 | 排序 |
|---|---|---|
| `projects` | `ownerOpenId` | `createdAt desc` |
| `inspections` | `projectId` / `inspectorOpenId` / `deleted` | `createdAt desc` |
| `inspection_items` | `inspectionId + deleted` / `inspectionId` / `projectId` | `sortOrder asc` |
| `reports` | `projectId` / `inspectionId + deleted` | `createdAt desc` |
| `users` | `openId`（唯一） | `updatedAt desc` |
| `app_settings` | `openId` | — |
| `privacy_requests` | `openId` | `createdAt desc` |
| `memos` / `chat_analysis` | `projectId`（遗留读写，无写入方） | — |

### 云函数

`ai`、`auth`、`inspection`、`project`、`report`、`settings`、`speech`（共 7 个在用；`setupdb` 为一次性脚本，刻意不部署）。
**8 个函数的 package.json 都没有声明 `timeout`**，全部使用平台默认值。

### 存储

`inspection-images/user/{openId}/`、`speech-input/user/{openId}/`、`logos/user/{openId}/`、`archive/…`。
照片以 **`sizeType: ["original"]` 上传原图**，全仓无 `compressImage` 调用。

## 三、头号问题：没有索引

### 为什么这是最急的

云开发数据库**按读取次数计费**。没有索引时，一个 `where` 查询要扫描整个集合：

- 集合 1000 行 → 每次查询读 1000 次
- 集合 10000 行 → 每次查询读 10000 次

也就是说：**打开一次报告列表的成本，随你的数据量一起涨**。慢和贵是同一个原因。

### 建议创建的索引

在 **云开发控制台 → 云数据库 → 集合 → 索引管理** 逐条创建（复合索引的字段顺序按「等值在前、排序在后」）：

| 集合 | 索引字段 | 类型 | 服务的查询 |
|---|---|---|---|
| `projects` | `ownerOpenId`↑ + `createdAt`↓ | 复合 | 项目列表 |
| `inspections` | `projectId`↑ + `createdAt`↓ | 复合 | 项目下的记录列表 |
| `inspections` | `inspectorOpenId`↑ + `createdAt`↓ | 复合 | 「我的记录」 |
| `inspection_items` | `inspectionId`↑ + `deleted`↑ + `sortOrder`↑ | 复合 | 报告条目读取 |
| `reports` | `projectId`↑ + `createdAt`↓ | 复合 | 项目报告列表 |
| `reports` | `inspectionId`↑ + `deleted`↑ | 复合 | 由巡查查报告 |
| `users` | `openId` | 唯一 | 账号读取（**必须唯一**，否则可能一人两条） |
| `app_settings` | `openId` | 唯一 | 报告资料读取 |
| `privacy_requests` | `openId`↑ + `createdAt`↓ | 复合 | 我的申请列表 |

> `users.openId` 与 `app_settings.openId` 这两条**建议设成唯一索引**：代码按 openId 取「最新一条」，若不唯一，并发写入会产生重复账号记录。

**创建索引不会丢数据**，可随时删除重建。建议**上线放量前就建好**——事后补建时，已有查询已经开始全表扫描了。

## 四、照片：成本的主发动机

### 事实

- 上传 **原图**（`sizeType: ["original"]`），手机拍摄单张常见 **3–8 MB**
- 报告里每张问题照片还额外存一张**标注图**（在原图副本上画编号）
- 报告分享给接收者后，对方**每次打开都重新下载全部原图**（`getTempFileURL` 签发的是原文件）

### 估算（按每张原图 5 MB）

| 规模 | 照片总量 | 存储 |
|---|---|---|
| 10 个活跃项目 | 200 张 | ≈ 1 GB |
| 100 个活跃项目 | 2000 张 | ≈ 10 GB |
| 1000 个活跃项目 | 20000 张 | ≈ 100 GB |

**流量是另一笔**：一个 3 张照片的报告被查看 10 次 ≈ 10 × 15 MB = 150 MB 出网流量。

### 建议（按性价比排序）

1. **上传前压缩**。这是投入产出比最高的一项：`wx.compressImage` 把长边压到 1600–2000px，体积通常降到 1/5 到 1/10，**巡查记录看编号和位置完全够用**。这一项能把上面整张表的数字除以 5。
2. **报告读者看缩略图，点开才加载原图**。列表与报告首屏用压缩版，用户主动放大时再取原图。
3. **未发布/已删除的记录，其照片及时清理**。目前删除是 `deleted: true` 软删，**云存储文件不会随之删除**（全仓 `deleteFile` 调用为 0）。这意味着删掉的项目，照片仍然占着存储和钱。

> 第 3 项要谨慎：软删是刻意的保护（误删可恢复）。建议做成「删除满 N 天后由运营者手动清理」而不是自动删。

## 五、成本与容量：什么时候要掏钱

云开发各资源有免费额度，超出后按量计费。**具体额度与单价以控制台实时显示为准**（套餐会变，本文不写死数字）。

需要盯的四项：

| 资源 | 什么时候开始告急 | 怎么降 |
|---|---|---|
| **数据库读次数** | 建索引后大幅下降；不建索引会最先超 | 建索引、减少不必要的轮询 |
| **存储容量** | 照片堆积，只增不减 | 上传压缩 + 清理已删除记录的文件 |
| **CDN 流量** | 报告被转发得多 | 缩略图 + 原图按需加载 |
| **云函数调用次数** | AI/ASR 调用，按次计费 | 见第六节的配额 |

**建议动作**：在控制台打开**费用告警**，设一个你心理上能接受的月度阈值（例如 50 元 / 100 元），到阈值发短信。不要等到账单出来才发现。

## 六、AI 与 ASR：必须加限额

### 现状

- `ai` 调腾讯混元（默认 `hunyuan-lite`），`speech` 调腾讯云 ASR，**按量计费**
- 代码侧**没有任何调用频率限制或日额度上限**
- 历史上出现过 HTTP 402（额度耗尽），代码对 402 有兜底文案，但**不会阻止继续消耗**

### 风险

一个用户反复点「AI识图」，或一批用户同时用，费用会**无上限增长**，而且失败之前没有任何预警。

### 建议

1. **在腾讯云控制台给这两个服务设用量告警**（最直接、无需改代码）。
2. **代码侧加日额度**：`ai_tasks` 集合已存在，可按 openId 统计当日任务数，超过阈值直接返回「今日 AI 次数已用完，可手动填写」。这是防误用与滥用的最低成本手段。
3. **监控 402**：一旦出现，说明额度已尽，应立刻收到通知而不是等用户反馈。

## 七、要盯什么（监控清单）

云开发控制台可看，建议**每周固定看一次**，出现异常再加密：

| 指标 | 在哪看 | 异常信号 |
|---|---|---|
| 云函数错误率 | 云函数 → 日志/监控 | 任一函数错误率 > 1% |
| 云函数超时 | 同上 | 出现超时（说明数据量或外部依赖变慢） |
| 数据库读次数 | 数据库 → 监控 | 与用户量增长不成比例地涨 → 索引没生效 |
| 存储用量 | 存储 → 用量 | 斜率突变 |
| 调用次数 TOP 函数 | 云函数 → 监控 | 异常集中的调用（可能是滥用） |
| 费用 | 费用中心 | 设阈值告警 |

**业务侧还应看**：每天新增项目数、新增报告数、AI 识图触发次数、语音转写次数。这四个数能解释绝大多数成本变化。

## 八、出事了怎么办（故障响应）

### 场景一：某个云函数报错率飙升

1. 控制台 → 云函数 → 该函数 → **日志**，按时间倒序看错误堆栈
2. 判断是**代码问题**还是**外部依赖**（腾讯云 ASR / 混元 返回错误通常是外部）
3. 若是刚部署引入的：**云函数支持版本回退**，在控制台把 `$LATEST` 指向上一版本，秒级回滚
4. 若是外部依赖：`ai` 与 `speech` 失败时**不应阻塞主流程**——手动填写与手动标注必须始终可用。这一点代码已按此设计，验证时请确认

### 场景二：数据库被写坏 / 误删

1. 控制台 → 云数据库 → **备份与回档**（如果已开启）
2. **现在就确认这个功能是否可用**——很多人在真正需要时才发现从未开过
3. 代码侧的保护：删除都是 `deleted: true` 软删，不会物理删除；报告有 `snapshot` 版本，重新生成不会覆盖历史

### 场景三：小程序本身出问题

1. **紧急回退**：公众平台 → 版本管理 → 「版本回退」，可退回上一个线上版本
2. 注意：**回退小程序不会回退云函数**。云函数要单独在控制台回退
3. 发布前务必按 [发布流程](发布流程.md) 冻结版本并留回执

### 场景四：AI/ASR 额度耗尽

- 用户会看到「额度不足，可直接按原文核对」
- **主流程不受影响**（手动路径完整）
- 立刻充值或临时关闭 AI 入口

## 九、数据治理

| 事项 | 现状 | 建议 |
|---|---|---|
| **备份** | 未知是否开启 | 立即去控制台确认；DB 备份**不覆盖云存储**，照片要单独考虑 |
| **保存期限** | 代码内无过期或定期清理机制 | 后台隐私指引里声明的期限必须与实际情况一致 |
| **软删数据** | 全部是 `deleted: true`，物理数据与云存储文件都还在 | 制定清理节奏，由运营者执行 |
| **历史报告编号** | 编号是**算出来的、不落库** | 品牌再变更会再次改写历史报告号，见《尺包品牌变更》 |

## 十、合规运营（上线后是义务，不是选项）

1. **权利申请必须有人处置**。现在申请会写入 `privacy_requests`（`status: received`），但**仓库内没有处理界面**，也没有时限约束。上线后这是法定义务。
   - 最低成本做法：每周固定查看一次 `privacy_requests` 集合，处理后手工把 `status` 改为处理结果，并在页面上回填 `response` 字段（页面已支持显示）。
   - 需要更规范时，再做一个运营端界面。
2. **注销 ≠ 删除数据**。当前注销只做到「受理」。若用户要求删除，需要人工到各集合清理该 openId 的记录**以及云存储里的照片**。
3. **建议指定一个人负责**。哪怕是你自己、每周半小时——**没有人负责的合规入口，等于没有**。

## 十二、随规模增长的检查点

把下面这张表当成「到了这个量，先做这件事」：

| 里程碑 | 先做什么 |
|---|---|
| **放量前（现在）** | ① 建全部索引 ② 开启 DB 备份并验证 ③ 开费用告警 ④ 确认 AI/ASR 用量告警 |
| 10 个活跃项目 | 看一次数据库读次数与存储用量，验证索引确实生效 |
| 50 个活跃项目 | 上线**照片压缩**；开始定期清理已删除记录的文件 |
| 100 个活跃项目 | AI/ASR 加日额度限制；把权利申请处置排进固定日程 |
| 500 个活跃项目 | 评估套餐档位；给报告分享做缩略图/原图分离 |
| 1000 个活跃项目 | 考虑把照片迁到独立 COS + CDN；重新核算单位成本 |
