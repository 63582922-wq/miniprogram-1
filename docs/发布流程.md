# 发布流程

> 2026-10-06 制定。起因见下方「为什么需要这份流程」。

## 一句话

**先冻结，再上传；验收的必须是即将提审的那个包。**

## 五个动作，顺序不能换

| # | 动作 | 完成标志 |
|---|---|---|
| 1 | **冻结** | 停止改代码。工作区干净（`git status` 无输出） |
| 2 | **提交** | 改动按层提交，每条 message 说清「改了什么、为什么」 |
| 3 | **打标** | 打一个 tag。**tag 名必须让人知道它对应什么** |
| 4 | **上传** | 上传后立刻记下版本号与回执文件路径 |
| 5 | **验收** | 在**刚上传的那个包**上做真机走查，记录设备与系统 |

## 三条硬规矩

### 1. 冻结之后不许再改

只要还有未提交的改动，就不能上传。上传的包必须能由某个 commit 完整还原。

### 2. tag 名不许撒谎

2026-10-05 建过一个叫 `v1.0.11-anchor` 的 tag。它**不是** 1.0.11 的源码，是 1.0.11 **之后**的工作区锚点。名字里带 `anchor` 就是为了防止有人 `git checkout v1.0.11` 之后以为拿到了线上代码。

**永远不要给一个还原不出对应源码的 tag 起版本号名字。**

### 3. 验收必须在待发布的包上做

在模拟器里、在旧包上、在"差不多就是这版"的代码上验收，都不算。验收记录要写清楚：**版本号 + 设备 + 系统 + 结果**。

## 为什么需要这份流程

2026-10-01 一天上传了 **12 个开发版本**（1.0.0 到 1.0.11），同时发生了三波云函数部署。到 2026-10-05 复核时发现：

- **没有任何文档记录 1.0.4–1.0.7、1.0.9–1.0.11 这 7 次上传**
- 文档里最新的版本号是 1.0.8，实际最后一个是 1.0.11（16:20）
- 工作区在上传后继续改到 21:03，**30 个客户端文件在末次上传之后又被改过**
- `ai` 云函数在部署后又被改动
- **1.0.11 对应的源码再也无法重建**——git 停在 09-27，没有任何客户端快照

代价不是"少了一个 tag"，而是：**出问题时无法回退到线上的那一版，也无法复现用户遇到的问题。**

## 每次发布的检查清单

```
□ git status 干净
□ node --test tests/*.test.cjs 全绿
□ node tests/local-compile.cjs 通过
□ git diff --check 通过
□ 按层提交，message 说清动机
□ 打 tag（名字与实际内容相符）
□ 上传，记录版本号 + 回执路径
□ 在刚上传的包上真机走查，记录 设备/系统/结果
□ 云函数如有改动，记录波次、目标环境与回退版本
□ 更新 docs/项目状态-<日期>.md
```

## 与云函数的关系

云函数部署同样适用冻结原则。客户端与服务端**各有一份部署包**，两者版本必须一起记录——只记客户端版本号，无法说明线上跑的是哪一版服务端。
